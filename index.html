Why OpenRAG

Four blocking points. Four answers.

Retrieval-Augmented Generation is becoming the standard way to access enterprise knowledge, but most existing tools hit critical limits.

The blocking point

Confidentiality gaps

Most RAG systems lack proper partitioning of data. Different users, teams, or departments often share the same index, creating risks of unauthorized access to sensitive information.

How OpenRAG answers it

Confidentiality first

OpenRAG supports secure partitioning of data per user or team, ensuring access control. Being fully open source and deployable on premises, it guarantees sovereignty and compliance.

The blocking point

Scalability issues

Standard RAG tools struggle when faced with millions of documents. Indexing slows down and retrieval quality drops, making them unfit for large-scale use.

How OpenRAG answers it

Handles massive document sets

With Ray-based distributed indexing, OpenRAG can scale to millions of documents across CPUs and GPUs, maintaining fast and reliable retrieval.

The blocking point

No parallelization

Ingestion and embedding are often sequential, with no distributed architecture. This leads to bottlenecks and very long processing times for big datasets.

How OpenRAG answers it

Parallelized architecture

Ingestion, chunking, and embedding are run in parallel across clusters, reducing processing time and enabling real-time knowledge base updates.

The blocking point

Poor document handling

Documents of different types are treated the same way. Complex PDFs, scans, or audio files are poorly parsed, resulting in weak indexing and irrelevant answers.

How OpenRAG answers it

Smart, type-aware indexation

Dedicated pipelines handle PDFs, images, audio, and scans with layout-aware parsing and OCR, ensuring accurate indexing for every format.

Architecture

Built to survive production.

Version 2 restructures OpenRAG into a hexagonal three-layer architecture, separating the domain from its adapters and its transport.

Application layers — v2.0.0

core/ — domain + ports services/ — adapters api/ — transport di/ — composition

Entry points

FastAPI — /docs Chainlit chat — /chainlit Admin console — /app/ OpenAI-compatible API — /v1

Indexing pipeline — scheduled on Ray

Marker — layout analysis Docling PyMuPDF OCR / VLM Speech-to-text Enriched Markdown Chunking Embedding

Inference servers

LLM — vLLM VLM — vLLM Embedder — Infinity Reranker — Infinity Transcription — Whisper

Storage

Milvus — vectors PostgreSQL — metadata, tasks, users

Retrieval that earns its answers

  • Hybrid search — semantic similarity combined with BM25 keyword matching.
  • Contextual retrieval — each chunk is enriched with a generated context sentence before embedding.
  • Multi-query and HyDE — reformulate vague queries, or generate a hypothetical answer to guide selection.
  • Multilingual reranking — Alibaba-NLP/gte-multilingual-reranker-base filters the top candidates.
  • Web search augmentation — optionally blend live web results alongside document sources, tagged separately in the response.

Scale without rewriting

  • Horizontal scaling — distribute processing across Ray worker nodes.
  • GPU acceleration — optimise inference across available hardware.
  • Resource management — intelligent allocation of compute across the cluster.
  • Monitoring — real-time cluster health and performance metrics.
  • Kubernetes and OpenShift — Helm chart published at oci://ghcr.io/linagora/openrag-stack.

Security & governance

Isolation you can prove.

Switch to another partition and ask the same question. The model answers that it does not know — because the documents are genuinely unreachable from there.

  • Partition isolation — each partition is a separate knowledge base, selected through the model id openrag-<partition>.
  • Workspaces — named subsets of files inside a partition, so search can be scoped further without restructuring anything.
  • Role-based access — owner, editor and viewer roles per partition, enforced by dependency guards on every route.
  • Hashed credentials — only a SHA-256 hash of each API token is stored; the raw token is never persisted.
  • Token or OIDC — bearer tokens for programmatic access, OpenID Connect with Keycloak or LemonLDAP::NG for people.

Hardened in v2.0.1

  • An empty partition scope now fails closed instead of searching everything.
  • Workspace file scoping is enforced all the way into Milvus.
  • Callers can no longer set the internal source field via REST metadata writes.
  • Web-search TLS verification is enabled by default.
  • Embedded HTML images are sanitised before indexing.
  • Plus SSRF guards, secret redaction, security headers, rate limiting and non-root images from v2.0.0.

Integration

It already speaks your stack's language.

OpenRAG speaks the OpenAI API language, making it easy to embed into chatbots, workflows, and enterprise systems. Integration is seamless, with minimal adaptation required.

openrag_example.py 
from openai import AsyncOpenAI, OpenAI

base_url = 'https://demo-openrag.linagora.com/v1'  # api base url
openrag_auth_key = 'sk-####'

async_client = AsyncOpenAI(api_key=openrag_auth_key, base_url=base_url)
sync_client = OpenAI(api_key=openrag_auth_key, base_url=base_url)

# The partition is selected through the model id
data_partition = 'digital-sovereignty'
model_id = f'openrag-{data_partition}'

chat_completion = sync_client.chat.completions.create(
    model=model_id,
    messages=[
        {
          "role": "user",
          "content": "Can you tell me about digital sovereignty in Europe?"
        }
    ]
)
response_content = chat_completion.choices[0].message.content
print(response_content)

Partition through the model id

There is no custom adapter to write. The partition is selected with the openrag-<partition_name> convention, which is what makes partition isolation work through a completely standard OpenAI client.

A major release rebuilding OpenRAG on a clean hexagonal three-layer architecture, followed by a stabilization release covering 55 merged pull requests.

v2.0.0 Hexagonal architecture 8 July 2026
  • Hexagonal architecture — restructured into core, services, api and di layers, improving testability and easing long-term maintenance.
  • New admin UI — React console: partitions, documents, jobs, users, model endpoints, pipeline presets.
  • Pipeline presets — named indexation and retrieval configuration bundles, assignable per partition.
  • Security hardening — search filter-injection fix, SSRF guards, secret redaction, security headers, rate limiting, and non-root images.
v2.0.1 Stabilization 23 July 2026
  • Tenant isolation hardened — three independent scoping fixes, including an empty partition scope that now fails closed.
  • Indexing reliability — re-indexing no longer duplicates chunks, and wedged Marker workers are reclaimed on parse timeout.
  • Retrieval correctness — multi-partition searches use each partition's own embedder, and streaming no longer drops the answer tail or its sources.
  • Admin UI — queue pressure and job duration, bulk cancellation, filtered CSV exports, plus accessibility and responsive fixes.

Deploy

Up and running with one command.

shell
# 1. Clone with submodules
git clone --recurse-submodules \
  git@github.com:linagora/openrag.git
cd openrag

# 2. Configure
cp infra/compose/.env.example infra/compose/.env
cd infra/compose

# 3. Launch (GPU)
docker compose up -d

# or, CPU only
docker compose --profile cpu up -d

Prerequisites

  • Python 3.12 or higher recommended
  • Docker and Docker Compose
  • For GPU machines, the NVIDIA Container Toolkit

Minimum specifications

  • Memory — 16 GB RAM minimum, 32 GB or more recommended
  • GPU — NVIDIA GPU with at least 16 GB VRAM
  • Unified-memory machines work with 16 GB, though 32 GB is recommended

Then open

  • /app/ — the admin console, on port 8081 by default
  • /chainlit — the chat UI
  • /docs — the full FastAPI documentation
